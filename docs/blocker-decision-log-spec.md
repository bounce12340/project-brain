## 建議最小範圍（待產品負責人確定政策才可實作）

一個**專案內的獨立清單**、兩種紀錄類別，不新增通知、AI 自動決策或跨專案彙總：

1. **卡關**：摘要、說明、狀態（open/resolved；預設 open）、提出者、建立時間；選填負責跟進者、預計處理日、解除說明／解除時間。解決只表示紀錄已解除，不自動變更專案／任務狀態或進度。
2. **待決策／已決策**：問題、必要背景、狀態（pending/decided；預設 pending）、提出者、建立時間；選填決策者、期限；變為 decided 時須填決策內容、決策人、決策時間。待決策不能偽裝已批准；已決策不能被 AI 自動產生或等同法規／人事批准。是否允許「撤銷／重開」先不定義。
3. 清單依建立時間排序、按狀態／類別篩選；每筆清楚標示提出者與更新時間。新建、編輯、狀態變更均須有權限檢查與足以追溯變更者及前後狀態的稽核；避免把完整敏感原文放 audit summary。只接受純文字，輸出安全轉義、限制長度；不附檔、不外送通知。
4. 保持既有進度紀錄／背景文意，不遷移舊自由文字、不重寫歷史、不改進度百分比。只在專案現有頁面加清單入口；MCP／AI 連接器、匯入、報表、郵件都不在首版範圍。若後續要連動，另列獨立需求與授權。

## 權限與驗收（提案，非已核定產品政策）

- 建議讀取沿用 `canViewProject`，不因知道紀錄 ID 而繞過專案可見性；沒有權限時不得回傳內容、不同專案 ID/紀錄 ID 不得交叉讀寫。
- 寫入策略**待決策**：建立可否沿用 `canEditProgress`？卡關解除／決策核定是否限 owner/admin、指定負責人或專案成員？避免用「一般成員可發進度」直接推論「可代他人做決策」。決策人必須是實際已授權且已登入的操作者，不接受客戶端偽造身分。若政策尚未定，先不實作 mutation。
- 驗收案例：可見者看同專案清單；不可見者與跨專案 ID 不能看、編、轉狀態；無權者不能把 pending 改 decided；欄位空白、過長、無效日期與非法狀態轉移回 4xx 且 DB 無部分寫入；合法變更保留建立時間與原提出者、寫稽核；並發解除／決策不得靜默覆蓋他人較新狀態；列表篩選及排序、手機版顯示、鍵盤操作與純文字 XSS 回歸。需以同一提交的實際本機測試及後續另授權的 CI／環境驗收，不能沿用基底 CI 當新功能證據。

## 待決策／阻礙

1. 誰能建立、編輯、解除卡關、核定決策？指定責任人是否需屬專案成員？admin/owner 是否能代決策？
2. 「已決策」能否撤銷、重開或修訂？法律／品質核准是否明確排除，是否要留版本化決策全文？
3. 卡關逾期與決策期限是否要提醒、通知誰、何時發送？首版預設**無通知**，不可自行啟用既有寄信。
4. 清單是否只在專案層級；跨專案儀表板、子專案彙整、API/MCP 暴露及敏感內容保存年限，均非此輪自動決定。
